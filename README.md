# OfficePulse Churn-Prevention CRM — end-to-end on Databricks

**Industry:** B2B SaaS / workplace technology (PropTech).
**Customer problem:** a Japanese SaaS vendor sells an office **attendance-detection** product (loaned sensors + mobile app) on annual contracts. Customer Success (CS) only finds out a customer is leaving when the customer files a cancellation ticket. That happens for fewer than half of churners, and the median ticket arrives **31 days before renewal**, too late to save the account. Product-usage data (GA4), support data (Zendesk) and contracts (CRM) are kept in separate systems, so nobody sees the decline coming.

> All names in this repo are fictional (vendor **CloudNest**, product **OfficePulse**, customer companies, people).
> All data is **synthetic**, generated by `notebooks/01_generate_raw_data.py`. No customer data is included.

## Business outcome (from the committed run, see `evidence/`)

| KPI (buyer's language) | Status quo | With this solution |
|---|---|---|
| Churning ARR caught **90 days before renewal** | 0% (cancellation tickets arrive at T-31 days, from 47% of churners) | **60.6%** (old rule score at the same alert volume: 53.9%) |
| Alert precision at T-90 | — | **63%** of flagged renewals really churn (rules: 59%) |
| ARR retained per year (30% save rate early vs 10% late) | ¥15.4M | **¥60.0M** → **+¥44.5M / year** |
| Gross Revenue Retention (trailing 12 m: ¥330M churned on ¥2.14B) | 84.6% | **86.7%** (+2.1 pts) |
| High-risk accounts CSMs have *not* flagged today | not visible | **see `evidence/job_run_summary.md` → business_impact** |

Model quality is measured **out of time**: the model is trained on renewals whose outcome was known before 2026-05-01 and tested on renewals after that date. ROC AUC is **0.847** for ML vs. **0.772** for the previous rule-based score; PR AUC is 0.621 vs. 0.393.

## How to reproduce

Prerequisites: Databricks CLI ≥ 0.290 authenticated to the workspace (`--profile <p>`), a serverless SQL warehouse, and a UC catalog you can create a schema in.

```bash
# 1. Data journey: raw → Lakeflow → UC → ML → scores → Lakebase → business case
databricks postgres create-project officepulse-crm --json '{"spec":{"display_name":"OfficePulse CRM"}}' --profile <p>
databricks api post "/api/2.1/unity-catalog/model-services?parent=schemas/<cat>.officepulse_churn&model_service_id=churn_advisor_llm" \
  --json '{"config":{"routing":{"destinations":[{"name":"primary","destination_type":"DESTINATION_TYPE_PAY_PER_TOKEN_FOUNDATION_MODEL","pay_per_token_config":{"model":"models/system.ai.databricks-claude-sonnet-5-5"},"traffic_percentage":100}]}}}' --profile <p>
databricks bundle deploy --profile <p>
databricks bundle run officepulse_churn_e2e --profile <p>

# 2. Genie space
python genie/create_genie_space.py --profile <p>

# 3. App: Lakebase role for the app service principal, grants, deploy
databricks postgres create-role projects/officepulse-crm/branches/production --role-id app-sp-crm \
  --json '{"spec":{"identity_type":"SERVICE_PRINCIPAL","postgres_role":"<app_sp_client_id>","auth_method":"LAKEBASE_OAUTH_V1"}}' --profile <p>
python lakebase/grant_app_role.py --profile <p> --sp <app_sp_client_id>
(cd app/frontend && npm install && npm run build)
databricks bundle deploy --profile <p>
databricks apps deploy <app-name> --source-code-path /Workspace/Users/<you>/.bundle/officepulse-churn/dev/files/app --profile <p>

# 4. Evidence
python scripts/export_run_evidence.py --profile <p> --run-id <job_run_id>
python genie/run_genie_evidence.py --profile <p>
python scripts/smoke_test_app.py --profile <p>
```

## Design decisions and trade-offs

- **Label = "does not renew at the next annual renewal", evaluated 30–180 days before renewal.** A naive "churn within 90 days" label is dominated by the renewal date: renewal timing alone scored AUC 0.91. That number looks good but has no value for CS.
- **Out-of-time split by renewal event**, not by snapshot date. When the same renewal appeared on both sides of the split, the model memorized accounts through seats and ARR (AUC rose to 0.96). Seats, ARR, days-to-renewal and tenure are therefore excluded from the model inputs. That costs about 0.01 AUC, and in return every SHAP driver is something a CSM can act on (detection rate, CSAT, urgent tickets, auto-renew).
- **Fair baseline.** The ML model is compared with the app's previous rule score at the **same alert volume**, and with the status quo (the customer's own cancellation ticket).
- **Accounts in their first 12 weeks are not scored.** Onboarding ramp-up looks like a usage decline, and the model was not trained on those weeks.
- **Lakebase publish via the job instead of Synced Tables.** Synced Tables need the Lakebase database registered as a UC catalog (`CREATE CATALOG` on the metastore), which this sandbox does not grant. The job does an equivalent transactional Delta→Postgres reload (≈56k rows in under 1 s). The app reads published tables and writes only to its own `crm_ops` schema, so republishing never overwrites operational writes.
- **The LLM explains and plans; it does not score.** The prompt is grounded on the model's probability and SHAP drivers. The call goes through a UC model service (Unity AI Gateway), so access is granted with `EXECUTE` and usage is governed.
- **Metastore tag policies** reserve common keys (`domain`, `pii`, …). Custom keys are used alongside the governed `system.certification_status=certified` and `class.*` tags.

## Running locally

```bash
cd app && pip install -r requirements.txt
export DATABRICKS_HOST=https://<workspace>  DATABRICKS_TOKEN=$(databricks auth token --profile <p> | jq -r .access_token)
uvicorn app:app --port 8000          # backend (Lakebase via OAuth DB credential, SQL warehouse, Model Serving)
cd frontend && npm run dev           # http://localhost:5173 (proxies /api)
```
Deploy the app at least once before running it locally, so that the app service principal (not your user) creates and owns `crm_ops`.
